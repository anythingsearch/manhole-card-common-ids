# マンホールカード取得状況 共通JSON交換仕様（基本ID版 version 2）

**2026年10月24日 — 双方合意済みの正式仕様**  
共同検討・仕様合意：public cardigan / blue25000  
従来の交換仕様：[version 1](https://github.com/anythingsearch/manhole-card-common-ids/blob/main/docs/exchange-format-v1.md)

この文書は**アプリ間でファイルによって取得済み状態と取得日を追加・補完する**ための交換仕様であり、完全バックアップ、削除同期、自動的な双方向同期ではありません。本仕様は非公式の共通交換仕様です。

> **合意済み：** `cards`維持、任意の`acquired_dates`、`YYYYMMDD`の文字列、取得日不明を許容、既存優先・未設定のみ補完、version 1読込継続・version 2保存、登録日時は交換対象外、基本ID単位、日付UIの有無に関係なく受信した日付を再出力する。  

## 1. ファイル構造

UTF-8で符号化したJSONファイル。拡張子`.json`。最上位はオブジェクトとする。

| 項目 | 必須 | 型 | 意味 |
| --- | --- | --- | --- |
| `format` | 必須 | 文字列（固定値） | `manhole-card-collection-exchange` |
| `version` | 必須 | 整数 `2` | 共通交換ファイルの形式バージョン |
| `cards` | 必須 | 基本ID文字列の配列 | 現在取得済みの基本ID。取得日不明でも必ず掲載 |
| `acquired_dates` | 任意 | `基本ID: 日付文字列`のオブジェクト | 日付が分かる取得済みIDだけ掲載 |
| `exported_at` | 任意 | タイムゾーン付きISO 8601の文字列 | **ファイル出力日時**。取得日でも登録日時でもない |

```json
{
  "format": "manhole-card-collection-exchange",
  "version": 2,
  "exported_at": "2026-10-24T15:00:00+09:00",
  "cards": ["13-225-A001", "31-364-A001"],
  "acquired_dates": {"13-225-A001": "20240510"}
}
```

- `cards: []` は取得済み0枚で有効。空配列を読み込んでも既存の取得済みは削除しない。
- 取得日が全件不明なら `acquired_dates` を省略できる。`acquired_dates: {}` も同等として読み込み可能とする（**追加提案**）。
- `cards`の順序は無関係。同じ基本IDの重複は1件として扱う（version 1の仕様を維持）。
- `acquired_dates`は、**同じ文字列の基本IDが`cards`に存在する場合のみ**設定できる。
- 追加の未知トップレベル項目があっても、既知項目の解釈を変えず無視できるものとする（**追加提案**）。ただし、`version`が3以上なら従来どおり全体拒否。未知フィールドの無条件保存は必須としない。
- ファイルサイズ上限、画面表示、ファイル名は各アプリで決める。極端に大きいファイルは安全のため各アプリが拒否してよい。

## 2. 取得日の意味と表記

- `acquired_dates`は利用者が**実際にカードを取得した日**を表す。アプリへの登録日時、取り込み日時、`exported_at`、ファイル作成日を代用しない。
- 値はASCII数字8桁の**JSON文字列** `YYYYMMDD`。例：`"20240510"`。
- 暦上実在する日付でなければならない。例：`"20240229"`は有効、`"20240230"`、`"20241301"`、`"00000000"`は無効。4桁年は`0001`〜`9999`。
- 未設定は**キーの省略**で表す。`null`、空文字、`"00000000"` は使わない。
- **今日より未来の日付であることだけを理由に共通ファイル全体を拒否する必要はない**（端末時計・タイムゾーン・後日取込による相違を避ける追加提案）。アプリの編集UIでは未来日の入力を制限してよい。
- 同一基本IDで通常版・特別版を共通管理する。版別ID（`-ja-a01`等）は直接交換せず、基本IDのみ出力する。
- UI上の自動記録、カレンダー入力、画面表示、取得日の手動修正は各アプリの判断でよい。自動記録するアプリであっても、共通ファイルの取り込み操作を新規取得操作と混同して、取り込み当日の日付を付与してはならない。
- **登録日時 (`registered_at` 等) は共通交換の対象外**。独自アプリ間同期で保存することは自由。

## 3. エクスポート

1. 現在取得済みのカードだけを選び、共通基本IDへ対応づける。既存version 1と同じ識別単位を使用する。
2. 同じ基本IDは重複を除いて`cards`へ出力する。順序は任意。
3. `cards`内かつ有効な実際の取得日が保存されているIDにのみ`acquired_dates`を付ける。
4. 日付が不明なら省略する。未取得IDは内部に取得日が残っていても**`cards`にも`acquired_dates`にも含めない**。
5. 新規保存は`version: 2`とする。version 1の書き出しは必須としない。
6. 取り込んだ取得日を**アプリ画面では使わない場合も**、内部保存し、当該カードが取得済みの間は次回version 2への再出力時に引き継ぐ。入力時に他アプリの既存取得日を勝手に捨てない。
7. 保存時に自動で取得日を推定・生成しない。`exported_at`を取得日に流用しない。

## 4. インポートの基本ルール

1. `format`、`version`、`cards`、存在すれば`acquired_dates`の構造と値を検証し、検証に失敗したら**カードの書き換え前にファイル全体を拒否**する。既存記録を部分変更しない。
2. version 1・2両方を読み込む。version 1には取得日がないため、既存の日付を保持し、新規に取り込むカードの日付は未設定のままにする。
3. 有効な`cards`は取得済みとして**追加**する。既存取得済みを削除せず、全件置換しない。
4. `acquired_dates`がある場合は、対象の取得済みカードに日付を紐づける。**既存の日付が設定済みなら既存優先**。既存日付が未設定のときだけファイルの日付を補完する。
5. 同じIDを何度読み込んでも取得記録を重複させず、既存のピン色その他の独自情報を変更しない。
6. 基本IDが自アプリのカードに対応づけられない場合は**そのIDだけ取り込まない**。他の正しいIDは処理し、件数と理由を案内することを推奨する（v1を踏襲）。そのIDの取得日も、別カードへ推測して付けない。
7. ファイルの読み込みは**削除・上書きの伝播を目的としない**。他アプリで取得日を訂正した結果を既存日付へ自動で上書きすることはしない。
8. 取り込み時のユーザー向けプレビュー・確認画面・独自バックアップは各アプリの自由。

| 取込前の取得日 | ファイルの取得日 | 結果 |
| --- | --- | --- |
| `20240510` | `20240515` | `20240510`（既存優先） |
| 未設定 | `20240515` | `20240515`（未設定を補完） |
| `20240510` | 未設定 | `20240510`（既存を維持） |
| 未設定 | 未設定 | 未設定（取り込み当日で補完しない） |

**特に重要：** アプリで「取得済みにする」と同時に現在日付を記録する場合も、**インポートでは取得日を自動生成しない**。インポートから新規取得済みとなるカードの日付は、ファイルに有効な日付がある場合だけ設定し、なければ未設定のままとする。

## 5. 細部の入力検証・例外処理

下表はversion 2対応アプリ間で合意済みの共通ルールとする。

| ケース | 合意済みの統一ルール |
| --- | --- |
| 必須フィールドなし／`format`・`version`不一致／`cards`の型違い | ファイル全体を拒否（従来のv1と同じ） |
| `acquired_dates`がオブジェクト以外（配列・`null`等） | **ファイル全体を拒否** |
| 日付が8桁ASCII数字の文字列でない／無効な暦日 | **ファイル全体を拒否**（無言で日付を捨てない） |
| `acquired_dates`のキーが`cards`に存在しない | **ファイル全体を拒否**（ファイル内の整合性違反） |
| `acquired_dates: {}` | 許容。省略と同義 |
| `cards`内の同じID重複 | 1件に統合。v1互換のまま |
| `acquired_dates`内のJSONオブジェクトのキー重複 | 書き出し禁止。読込時に検出できるなら拒否を推奨（標準JSONパーサーの差を考慮し、検出機能までは必須にしない） |
| `cards`に未対応IDがある | v1と同様そのIDのみ除外。他の正しいIDは追加。該当取得日も除外 |
| 未知のトップレベル項目 | 既知項目の検証に成功していれば無視可（将来の拡張に配慮） |
| `version: 3`等、未対応バージョン | ファイル全体を拒否 |
| `exported_at`の省略 | 許容。記載時はタイムゾーン付きISO 8601の日時文字列を出力。取得日として使用しない |
| 端末日時より未来の暦日 | 未来という理由だけでは形式エラーにしない。各アプリは入力UIで制限・注意喚起してよい |

**処理順（重要）：** まずファイル全体の構造と`acquired_dates`の整合性を検証する。それから各IDが自アプリで取り込めるか判断し、対応できるIDだけ追加・補完する。無効ファイルの途中まで取り込んでしまわないこと。

## 6. 旧番号・新番号の同一視について（version 1の例外を維持）

version 1の正式仕様書では、次の例は**blue25000のAndroid/iOSが同一カードとして扱う例外**であり、第三者アプリの一律必須規則ではない。

| 対象 | 旧番号 | 新番号 |
| --- | --- | --- |
| 小樽市 | `01-203-A001` | `01-203-A002` |
| 豊富町 | `01-516-A001` | `01-516-A002` |
| 尾張旭市 | `23-226-A001` | `23-226-A002` |

- **新しい同一視ルールをv2で勝手に追加しない**。各アプリで既存の正式な対応関係が確認されている範囲に限定する。
- アプリが取得済みIDを**既存の明示的な対応表によって別の基本IDへ正規化する場合、紐づく取得日も同時に正規化しなければならない**。IDだけ変換して日付を破棄してはいけない。
- 元ファイルに旧番号と新番号の両方が含まれ、同一カードとして取り扱うアプリ内で**取得日が異なる場合**：すでにそのカードに日付が設定済みなら既存優先。既存が未設定なら、入力側にある**最も古い有効な取得日**を採用する。
- そのアプリが旧新番号を別カードとして管理している場合は、通常の別基本IDとして扱う。**すべてのアプリに統合を強制しない**。
- 同一視できないIDを、文字列の類似だけで別IDへ転記してはならない。

## 7. 未取得へ戻す／日付を削除する場合の意味

- 共通ファイルのインポートは**追加・補完**であり、既存情報の削除や日付の消去を伝播しない。
- 例：Aで取得日を手動で「未設定」に戻してv2書き出ししても、Bに以前の取得日があれば、Bはそれを**保持**する。Bの取得日を消去する意味にはならない。
- 同様に、Aで「未取得に戻す」操作をして書き出しても、Bの取得済み状態は**解除されない**。
- `acquired_dates`からIDが省略されている状態は、「このファイルは取得日を知らない」の意味であり、「他のアプリの日付を削除せよ」の意味ではない。
- この制限はversion 2の既存優先ルールの帰結であり、今回**削除同期や強制上書きの新仕様は追加しない**。
- 誤操作に備え、未取得へ戻した時も取得日をアプリ内部で残しておくことを推奨する。ただし内部データ保持方法・ユーザー編集機能はアプリごとに自由。

## 8. アプリ間往復と、日付表示機能がないアプリ

- 例：アプリA（取得日UIあり）→アプリB（取得日UIなし、ただしv2対応）→アプリC（取得日UIあり）と転送しても、**Bが取り込めた基本IDの取得日はBのv2書き出しに残る**。
- Bが元からそのカードの取得日を持つ場合は、Bの既存日付を優先する。したがって、「Aのファイルのすべての値を無条件にそのまま出力する」義務ではない。
- Bが取得日を新たに記録する機能を持たない場合、Bで新たに取得済みにしたカードは日付未設定でよい。
- Bで対応不能のカードIDを受け取った場合、v1と同様スキップしてよく、**未知のカードまで保持することは必須としない**。ただし、Bが日付UIを持たないことのみを理由に、対応済みカードの取得日を捨ててはいけない。

## 9. version 1との互換性

- version 1（`version: 1`）は従来の定義どおり読み込む。version 1の`exported_at`を取得日に利用しない。
- version 2の書き出しは`version: 2`のみでよい。**旧v1しか理解しないアプリがv2を読めない**ことは既知の制約であり、双方でv2対応へ更新する方針。
- 取得日が訂正されたときに、共通ファイルの再取り込みで既存を上書きすることはない。手動修正の可否は各アプリ独自。
